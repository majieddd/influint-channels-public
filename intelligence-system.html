Intelligence system

Every layer the pipeline runs through, what each one does, and the gate it has to clear. This page exists so the logic can be read and challenged by a person, separately from the findings it produces. The analyst traces below show the same method applied to a specific video.

Data in→Retention arithmetic→Evidence→Written notes (the only model step in analysis)→Census: which beat works→Formats and ideas→Action list→Probes: code owns the number→Ledger and the evidence ladder→Binding audit→Checks the record runs on itself→Adjudication queue and memory→The brief back into the tools

1 · Data in

Retention curves, per-video stats, CTR and viewer cohorts arrive from the Analytics API, a Studio session, a data sheet, or a public seed. Every video is stored field by field (a run never erases what another run measured) and the video SET is a union.

Gate: Non-public videos are pruned against the public Data API. Public seeds carry LIFETIME views and are stamped as such.

src/lib/site/profile.ts · scripts/prune-nonpublic.ts

2 · Retention arithmetic

Each curve becomes a hazard rate (share of viewers PRESENT who left at each moment), baselined against the previous five moments and ranked by excess viewers lost. Rises split into real rewinds and skip-forward landings by curve shape.

Gate: A floored baseline so a quiet window cannot yield infinity; rank by excess lost, never by ratio alone; every drop compared with the channel's own median at fixed clock marks.

src/lib/analysis/retention.ts · retention-benchmarks.ts

3 · Evidence

The public transcript and seek-preview frames are fetched for every flagged moment, so a note quotes what was actually said at that second.

Gate: A moment without a supplied timestamp is dropped; a video without captions falls back to check-this-timestamp language and says so.

src/lib/youtube/public-video.ts

4 · Written notes (the only model step in analysis)

One model call per video writes WHAT (observable, with the figures in one italic parenthetical), WHY (a check at that timestamp, or the transcript quote), HOW (the next move), plus a rationale and a caution that downgrades the verb when the data cannot settle it.

Gate: Universal truths are banned: an observation must carry the comparison with the channel's own median or be omitted. Fabricated timestamps are dropped. The brief of established claims and prohibitions rides in the prompt with routing mode and provenance.

src/lib/insights/video-retention.ts · src/lib/intelligence/brief.ts

5 · Census: which beat works

Every flagged moment across the recent cohort is grouped by WHAT IS HAPPENING (the model groups, blind to whether it was a drop or a peak), then each group is measured against its own kind's band norm.

Gate: Categories holding over half the moments or built from contiguous rows are rejected; instances before 0:30 never rank; a sign test p is reported.

src/lib/analysis/moment-census.ts

6 · Formats and ideas

Statistics first: recurring title frames are mined; then one model call assigns every video to a repeatable shape; arithmetic last computes each shape's median outlier score. Ideas cross a proven shape with a surging subject; the projection is channel median × the format's observed lift, never a model's number.

Gate: Formats echoing the prompt's examples, holding over a share cap, or built from contiguous input rows are rejected. Era-confounded formats get no multiplier. Cited evidence ids that were not supplied are dropped and counted.

src/lib/site/channel-formats.ts · src/lib/ideas/*

7 · Action list

Curves, formats and cadence collapse into an ordered list of moves with NO model involved: the same data twice gives the same list. Each action carries its chart and its confidence read off the evidence ladder.

Gate: Absences are rendered (what was checked and came back healthy). A bimodal cadence reports the spread instead of a false rhythm.

src/lib/insights/action-list.ts

8 · Probes: code owns the number

A fixed battery of measurable predicates runs over the data every analysis already has: Spearman rank correlations, delta-medians with per-side floors, proportions, calibration against a claim's own asserted number.

Gate: Null below minN (silence is the honest answer). Views are age-normalised against temporal neighbours. Each result carries its views basis and probe version.

src/lib/intelligence/probes.ts

9 · Ledger and the evidence ladder

Each claim's own evidence database: one observation per channel per day, stamped with the channel's strata. Standing derives from it: theory → candidate-law → law (human-signed only), warning, rejected. Standing moves both ways.

Gate: Only first-28d-basis, current-version rows feed figures. Killing takes as much evidence as promoting (3+ channels). Niched claims grade in-niche. A signature is never erased by data; disagreement is flagged, not resolved silently.

src/lib/intelligence/ledger.ts · store.ts

10 · Binding audit

A model proposes which probe tests each claim; a second, adversarial pass re-judges each binding one at a time against the probe's exact arithmetic, told to reject by default.

Gate: One-way gate: a passed binding is never re-litigated unless the arithmetic changes. Wrongly bound is worse than unbound.

scripts/bind-levers.ts · scripts/audit-levers.ts

11 · Checks the record runs on itself

Consistency (contradictions, redundancies), depth-vs-count (video-weighted, effect intervals, risk asymmetry, niche make-up per side), niche divergence, refinement of asserted numbers, discovery of unclaimed patterns.

Gate: Every check FILES; none moves a standing. Discoveries enter as candidate-law with the binding pre-audited because the claim was written from the probe's own result.

consistency.ts · depth.ts · scoped-strength.ts · refine.ts · scripts/discover-patterns.ts

12 · Adjudication queue and memory

Everything only a person may settle, with full context: claim wording, bars per reading, sides with depth, per-channel chart, prior decisions on the same subject, the gate that fired and the concrete action. Recurring resolution reasons are proposed as principles.

Gate: Items lapse when undetected (lapsed is not settled); resolution requires a name; events never lapse. Usage heat orders theories; archive means out-of-briefs only.

src/lib/intelligence/adjudication.ts · scripts/intel-sync.ts

13 · The brief back into the tools

Every generator and analyser receives the store as instructions: laws first, standings stated, contested claims flagged, refuted claims as prohibitions, claims bound to the run's own measurements listed first.

Gate: Routing mode is stamped in the header so a widened pool never masquerades as a routed one. Every measured line carries derived provenance.

src/lib/intelligence/brief.ts

Processes by deliverable

The layers above are the order of the logic. The work is shaped by what is being delivered: each deliverable is a department's pass over the same record, defined by its link to clickability, watchability and replayability so its effect can be cross-examined against the others, and each writes back to the channel's knowledge base so the next one starts further along. The general channel audit comes first.

1 · Channel audit

The general pass, first: clickability (impressions to views to engaged views, with CTR at each step), watchability (AVD and APV together, the curves, the overlay), replayability (returning, regular, casual and new viewers, net subscribers, rhythm).

Runs: Studio pull or Analytics API; regression cohort; V3 deck and sheet; dimensions header; "What the numbers show"; action list.

Dimension: All three dimensions, in that order.

src/lib/output/slides.ts · src/lib/site/dimensions.ts · src/lib/site/channel-charts.ts · src/lib/insights/action-list.ts

2 · Ideation audit

Three rings: the channel's established ideas and what the marketplace already rewards; what the community and competitors ship; the landscape beyond, with the abandonment test applied before any expansion is proposed (a large, held audience is moved at a cost; a genuinely different audience deserves a second channel).

Runs: Format library; peers resolved then crawled; trending and search; recombination with arithmetic projections; a published idea set.

Dimension: Clickability first (does the premise earn the click on this audience), then replayability (does it bring them back).

src/lib/ideas/* · src/lib/site/channel-formats.ts · scripts/ideas-pipeline.ts

3 · Packaging audit

Visual format, title format and idea format, and how they combine: which combinations synthesise into the most clickable package, and what those combinations do to watchability and replayability, so a package that clicks and bleeds is caught.

Runs: Thumbnail read on real thumbnails; title-lead and keyword bars; length against CTR; superlative and numbered families against their fleet records; openings against the first minute; a study with angles, charts, claims, mocks and a Test & compare plan.

Dimension: Clickability, then the watchability check that a package which changes who arrives changes who stays.

src/lib/site/study.ts · data/studies/<channelId>/

4 · Retention audit (creative and content)

What happens inside the video: hazard at each flagged moment against the channel's own benchmarks, replay peaks separated from skip landings, the sponsor read measured as bleed depth in its own category, WHAT / WHY / HOW with a transcript quote and the frame at that second.

Runs: Curve (API or Studio); transcript and frames; per-video notes; moment census; the retention section of a study.

Dimension: Watchability, with the replayability check that a beat viewers scrub back to is a premise worth repeating.

src/lib/analysis/retention.ts · src/lib/insights/video-retention.ts · src/lib/analysis/moment-census.ts

5 · Production and post-production

The cost side of every finding: runtime, cadence, the effort a shape demands, sponsor placement and cross-cutting, the opening's promise delay, the outro.

Runs: The same curves and the rhythm strip, filed against the dimension each moves.

Dimension: A cross-cut read is a watchability finding; a held rhythm is a replayability finding.

src/lib/analysis/segments.ts · src/lib/site/channel-charts.ts

Two facts about the server as found. Nothing was loaded (lms ps: no models), so the first call pays a load of the 16.5 GB build; lms load esatapedico/qwen3.8-27b-nvfp4-mtp --gpu max --context-length 16384 ahead of a run avoids that inside the loop's timeout (measured: 23.2 s to load, 15.3 GiB resident, four parallel slots).

The load flag that matters more than the build. Loaded with its defaults the model reserves its full 242,010-token context, and on this 24 GB card that puts prefill on a slow path: a 4,238-token prompt took 237 s to first token (about 18 prompt tokens per second) and decoded at 14 tokens per second, and the Q4_K_M build loaded the same way did not answer the same prompt inside ten minutes. Reloaded with --context-length 16384 the same NVFP4 build takes a 4,153-token prompt to first token in 2.3 s and decodes at 60.6 tokens per second; a short prompt answers in 0.38 s. A hundredfold difference in prefill from one flag, and it is the flag no harness sets for you. Every harness figure in the section below was taken under the default load, before this was found, so the absolute times there are an order of magnitude pessimistic; the comparison between the two harnesses stands, because both paid the same price. And the HTTP server requires an API token (/v1/models answers invalid_api_key without one); the client already sends LOCAL_LLM_KEY as a bearer, so the token created in LM Studio goes there. The token is the operator's to create, so the live measurement for this note went through the CLI instead (lms chat <model> -p ... --stats), which needs none.

What autoresearch is, precisely

The skill is a protocol for the agent that runs it, not a program. Setup: read the scope, define a mechanical metric and its direction, define a verify command and dry-run it, an optional guard that must always pass, a results log, a baseline as iteration 0. Then the loop: review the state and the log, pick one change, make it, commit, verify, guard, keep or revert, log, repeat; bounded through /loop N. Its one hard requirement is a metric that outputs a number, and its one memory is git.

That gives "run it with the local model" two readings:

  1. Claude Code runs the loop and calls the local model for the ideation step. Cheap proposals, frontier orchestration. It still needs a session and frontier tokens for every iteration, so it is not autonomous in the sense asked for. It is the right way to develop and validate a loop before it runs alone.
  2. A standalone runner implements the same protocol with the local model as the ideator and code as the verifier. No frontier model in the loop. scripts/agent-loop.ts is the skeleton: the objective file as the steering wheel, reports only, never executes free text, everything written under data/agent/. This is what autonomy means here, and the rest of this note is about it.

The split that makes it safe, and where it breaks

The pipeline's standing rule is that a model decides WHAT and code decides HOW MUCH: every projection, statistic, score and standing is arithmetic. Autoresearch's keep-or-discard gate is a mechanical metric, so a small model's whole job inside the loop is to choose the next thing to try. That is the part a local model can do.

The benchmark that ran the real format-classification prompt through four local models (the Ollama set, before LM Studio was the endpoint) is the boundary. Every parseable run produced valid JSON with no fabricated video ids, so the guards never fired, and what would have shipped was the prompt's own example templates echoed back, a single format holding 59 of 60 uploads, and formats built from consecutive rows of the input. The dangerous outputs were the ones that looked like they worked; the safe failure was gemma4:12b returning nothing and being caught. The lesson is specific: where the model's output is itself the input to a statistic, a small model is unsafe without a code gate that can reject and a frontier audit before anything enters the ledger. The lever audit, a yes-or-no judgement one binding at a time, measured 3 of 3 correct at about five seconds a call, and is the kind of task that delegates.

Guardrails that do not move

  • Standing moves stay human. The loop never writes standings or signatures in claims.json; observations reach the ledger only through the existing retest and discover code paths, which stamp basis, version and strata.
  • It never publishes, never runs an analysis pass, never edits claims text. Proposals land on the adjudication queue; everything else lands under data/agent/autoresearch/<run>/ (a results log with the metric before and after each iteration, the model name, the change) and on a git branch per run for code-scope loops.
  • Gates and thresholds are read-only scope: CHANNELS_FOR_CONSISTENT, every probe's minN, the 0.2 correlation gate, the 75% held gate. "More discoveries" is trivially gamed by loosening them, and the discovery run has already been bitten once by a hard-coded held: true. The guard diffs those files and fails the iteration on any change.
  • Bounded runs (/loop N or a MAX_ITER), a wall-clock budget, and the existing per-call timeout so a wedged model cannot hang the loop.
  • The objective file stays the steering wheel. An empty file means testing mode, exactly as today.

The model question

Recommendation: Qwen3.8-27B in the NVFP4 + MTP build for both loops, on LM Studio. It is one model rather than two, it fits the 5090 with context to spare, and its published coding and agentic results are the strongest of anything on the box, which is what loop 2 (composing probe arithmetic) needs. Three settings matter more than the choice of build: reasoning_effort low for loop 1's yes-or-no judgements and higher for loop 2's code, temperature 0 (the client's default), and a per-call timeout that survives the first load. The selection rule does not change: agreement with the frontier's 68 audited bindings, and a model below about 90% agreement on the drops does not judge bindings unattended, whatever it scores elsewhere. The Ollama models (gemma4 31B, qwq 32B, qwen3-coder 30B-A3B) enter the same benchmark as controls, because nothing about a model's size or reputation settles this: the format-classification benchmark was the reminder that the plausible-looking model is the one to distrust.

The harness question: Hermes or pi

The operator's preference is Hermes Agent as the harness that drives the local model, tested against pi (the minimal coding agent). Both are installed on the box: Hermes Agent v0.20.5 (native Windows, %LOCALAPPDATA%\hermes, its own config, memory, skills and a yt-audit MCP server already registered) and pi 0.84.4 (@earendil-works/pi-coding-agent, with an lmstudio provider already defined in ~/.pi/agent/models.json pointing at the NVFP4 build under the identifier qwen38-nvfp4). Both are protocols over an OpenAI-compatible endpoint, so the model, the endpoint and the token are shared; what differs is everything around the model.

What each is. pi gives the model four tools (read, write, edit, bash), a small system prompt, and a print mode that emits every event as JSON lines; it does nothing else. Hermes gives it a toolset system (terminal, file, web, browser, memory, delegation, cron, skills and more; 40-plus tools), persistent memory across sessions, an auxiliary model for side jobs (session titles, compression, approvals, curation), fallback providers, a gateway to messaging platforms, and a kanban and cron scheduler: a personal agent that happens to run tasks, rather than a task runner.

What the smoke tests showed before any task ran.

  • Hermes reached LM Studio with its own stored key, enabled a four-tool file toolset, and sent a 7,034-token first message for a one-line question. Its auxiliary title-generation call went to the same local model, timed out twice at 30 s while the main generation held the GPU, and fell back to a paid OpenRouter lane (google/gemini-3.6-flash, with the log itself warning of real spend). For the test auxiliary.free_only is set to true so the comparison cannot spend credit; it is the one change made to the operator's Hermes configuration and it is noted here to be reverted or kept as they prefer.
  • pi answered the same one-line question in 56 s with no tools, JSON events, and exit 0, once LM_API_TOKEN was present; without it, a clear one-line refusal. The token was bridged into the test shell from the variable Hermes already keeps, never printed.
  • Both need the same fix on this box: Hermes's --usage-file is a top-level flag, and pi resolves only from the tool's Git Bash (cmd.exe and Python see a different global npm tree), so each runner drives its harness from the environment where it resolves.

The protocol. Three sandboxed tasks, each a fresh copy of a template with a mechanical verifier (node --test), a working directory the harness is pointed at, and a tree diff afterwards: t1 implement a tie-aware Spearman correlation until the tests pass (tools: read, write, edit, bash); t2 add a probe to a small registry following its pattern, the loop-2 shape (same tools); t3 eight binding-audit judgements written to a file with no commands allowed (read, write). Each run records verify pass or fail, wall time, exit code, tool turns and tokens where the harness reports them, every file changed, whether a protected file (the verifier, the fixture) was touched, and for t3 the agreement with the audit. Same model, reasoning_effort low, one run per cell first, repeats where the cells disagree. The verifiers were themselves checked to fail on the untouched template and pass on a reference solution before any model time was spent; the first version of one of them was an empty file that passed everything, which is the kind of thing this note exists to record.

What the runs showed. Both harnesses completed all three tasks with the verifier passing, touched only the file the task named, and matched the frontier audit on all eight judgements. The difference is overhead, not capability.

  • pi was faster on two of three (t1 347 s against 942 s; t3 321 s against 504 s) and sent a third of the prompt tokens on every task, because its system prompt is small and it adds nothing between calls. Hermes was faster on t2 (769 s against 1,066 s), where pi's model thought at length (8,460 output tokens against 2,908) and paid for it under the slow prefill; that is a reasoning_effort and prompt-cache effect, not a harness one, and it will shrink with the context capped.
  • Hermes's opening call cost 313 to 667 s on every run: a 5,300-to-6,600-token first message (its tools, rules and memory) processed at the default load's prefill speed. With the context capped that becomes a few seconds, and the fixed prompt is then a token cost rather than a time cost; it stays two and a half times pi's.
  • Hermes exited cleanly on each task, but its --run-budget is a wrap-up notice injected into the conversation, not a stop; a run killed from outside left a grandchild retrying against the model and the next run's first call took 1,864 s. An unattended loop needs --max-turns as the real ceiling and a runner that kills the process tree.
  • Hermes's auxiliary calls (session titles, compression) go to the same local model and, when it is busy, time out and fall back to an OpenRouter lane that can be paid; auxiliary.free_only: true closes that. pi makes no side calls.
  • pi's JSON event stream gives turn, tool and usage counts for free; Hermes's come from its own log. Both are enough for a results log.

Verdict. As the harness for an unattended autoresearch loop, pi functioned better: less overhead per call, no side calls, a clean exit, machine-readable events, and nothing to configure beyond the token. Hermes functioned as well on the work itself and brings what pi lacks (persistent memory, skills, the yt-audit MCP server already registered, a gateway to messaging), at two and a half times the prompt cost per call and with three settings that must be made for it to be safe to leave alone: auxiliary.free_only: true, --max-turns as the hard stop, and the context-capped load. The shape that fits both preferences: pi (or a direct API call, since loop 1's ideation step needs no tools at all) as the inner engine of the runner, and Hermes as the operator-facing agent that reads the results log, files proposals and answers questions about them. If Hermes is to be the inner engine too, it works, with those three settings and the measured overhead.

What this does not solve

A local model reaches no further into the knowledge base than the probe battery does. Most of the store is about packaging, thumbnails and audience psychology, which no probe over stored curves and titles can measure, and a loop only widens measurement through new probes over data the store already has. Coverage still depends on access grants and Studio pulls more than on autonomy.
